# Agent Instructions

## Workspace Guidance

Use this file for project-specific preferences, recurring workflow conventions, and instructions you want the agent to remember for this workspace. Keep durable facts about the user in `USER.md`, personality/style guidance in `SOUL.md`, and long-term memory in `memory/MEMORY.md`.

## Scheduled Reminders

- Before scheduling reminders, check available skills and follow skill guidance first.
- Use the built-in `cron` tool to create/list/remove jobs (do not call `nanobot cron` via `exec`).
- Get USER_ID and CHANNEL from the current session (e.g., `8281248569` and `telegram` from `telegram:8281248569`).

**Do NOT just write reminders to MEMORY.md** — that won't trigger actual notifications.

## Heartbeat Tasks

`HEARTBEAT.md` is checked periodically by the protected heartbeat cron job that `nanobot gateway` registers when `gateway.heartbeat.enabled` is true. Do not create a duplicate heartbeat job unless the user has disabled the built-in one and explicitly wants a custom schedule.

- Use `apply_patch` for normal task-list updates, especially when adding, removing, or changing multiple lines.
- Use `edit_file` only for small exact replacements copied from the current `HEARTBEAT.md`.
- Use `write_file` for first creation or intentional full-file rewrites.

When the user asks for a recurring/periodic heartbeat task, update `HEARTBEAT.md` instead of creating a one-time reminder. Use the built-in `cron` tool for separate reminders or custom schedules that should not be part of the heartbeat task list.

# 智成安监系统隐患排查报告生成约束

## 1. 入口与主流程

当用户上传图片、视频、压缩包等现场素材，并要求进行隐患识别、安监检查反馈或报告生成时，启用 `zhicheng-hazard-report` Skill。

完整报告任务必须严格按照 Skill 中 `references/workflow.md` 的完整流程执行，**不得跳过任何步骤或偷懒简化**：

1. **第一步**：执行 `extract_checklist.py` 提取检查清单
2. **第二步**：执行 `match_hazard.py` 匹配隐患
3. **第三步**：执行 `build_report_json.py` 构建报告 JSON
4. **第四步**：**模型手动选择条款**，将选择结果写入 `_state.hazards[].resolution`（没有自动选条款脚本）
5. **第五步**：执行 `validate_report_json.py` 校验报告 JSON
6. **第六步**：执行 `report_generator.py` 生成 PDF/Word 报告

**禁止事项**：
- 禁止跳过脚本流程直接手动分析
- 禁止省略任何步骤
- 禁止让脚本代替模型选择条款
- 禁止未通过校验就生成报告

纯文字咨询仅做常规问答，不生成报告。

---

## 2. 输出顺序

完整报告任务必须按以下顺序执行：

1. 先输出 Markdown 快速反馈。
2. 再默认生成 PDF 报告。
3. PDF 生成并发送后，再询问用户是否需要 Word 版本。
4. 不要一次性同时生成 PDF 和 Word，除非用户明确要求。

Markdown、PDF、Word 必须基于同一份最终报告 JSON，不得分别生成两套数据。

---

## 3. Markdown 快速反馈强约束

Markdown 快速反馈必须严格使用 Skill 中 `report-output-format.md` 的模板。

必须满足：

* 标题使用：`## 📋 成都院智成安监检查反馈意见（{timestamp}）`
* 只包含 4 个部分：

  * 基本信息
  * 场景认定
  * 总体评价
  * 隐患清单
* 不得包含“下一步安全生产工作提醒”。
* 隐患清单只展示重大事故隐患，不展示一般事故隐患。
* 禁止使用 Markdown 表格。
* 隐患清单必须按照片分组。
* 每个照片分组使用：`**📷 文件名.jpg**`
* 每个照片分组下方必须插入图片：`![现场照片](图片URL)`
* 图片 URL 必须来自最终 JSON 的 `image_url_map`。
* 禁止暴露本地路径。
* 禁止绕过 `image_url_map` 另行上传或编造图片链接。
* 备注统一填写：`建议按现场实际复核`。

---

## 4. 多照片处理强约束

用户上传 N 张照片，报告中必须体现 N 张照片，不得遗漏。

多图处理时必须逐张独立分析，不得一次性把多张图混合判断。

必须做到：

1. 建立“真实文件名 → 图片 URL → 隐患结果”的一一映射。
2. 必须使用用户提供或系统传入的真实文件名。
3. 每条隐患必须绑定对应照片的 `photo_name`。
4. `photo_name` 必须能在 `image_url_map` 中找到对应 URL。
5. Markdown 中每个照片分组必须使用正确文件名和正确图片 URL。
6. PDF/Word 中同一照片对应多条隐患时，照片单元格必须 rowspan 纵向合并。

禁止事项：

* 禁止用 `img_001.jpg`、`现场照片1.jpg` 等虚构文件名替代真实文件名，除非系统本身只提供该标准化文件名。
* 禁止将 A 照片的隐患写到 B 照片下。
* 禁止遗漏用户上传的任何一张照片。
* 禁止在报告中出现本地图片路径。

---

## 5. 隐患识别强约束

隐患识别必须遵循“先客观描述，后隐患推导”。

只能根据图片、视频、用户说明或系统上下文中明确出现的事实判断，不得补造画面中没有的人员、设备、工序或状态。

特别禁止：

* 图片中没有人员，不得推导人员类隐患。
* 图片中没有头部或安全帽，不得推导安全帽类隐患。
* 图片中没有火源、烟雾、焊接、切割等明确动火迹象，不得推导动火或火灾类隐患。
* 图片中无法确认设备类型时，不得强行套用特种设备、起重机械等条款。
* 一般隐患不得为了凑“重大事故隐患”而强行引用重大隐患判定条款。

---

## 6. 条款引用强约束

隐患引用规范条款时，必须严格遵循 Skill 中 `citation-rules.md`。

每条隐患必须包含：

* 规范名称
* 条款号
* 条款原文

条款原文必须逐字复制，不得改写、截断、概括或补充。

引用前必须确认：

1. 规范文件真实存在于 `references/` 中。
2. 条款号在该规范文件中真实存在。
3. 条款原文来自该条款。
4. 条款内容与隐患事实直接对应。

禁止事项：

* 禁止隐患描述与条款内容不匹配。
* 禁止条款号正确但条款原文错误。
* 禁止凭记忆编造规范名称、条款号或条款内容。
* 禁止把 A 类隐患套用 B 类条款。
* 禁止把一般问题套用不相关的重大隐患条款。

典型错误必须避免：

* 装载机违规加装叉车属具，不得套用“主要受力构件有裂纹”类条款。
* 沟槽开挖未支护，不得随意套用“土方超挖”类条款，必须确认条款事实是否直接对应。

若无法找到可靠条款，不得编造，应停止最终报告生成并说明“条款需进一步核实”。

---

## 7. 候选条款选择强约束

候选隐患和候选条款由 Skill 脚本生成后，模型必须自行完成相关性判断，并将最终选择写入 `_state.hazards[].resolution`。

禁止事项：

* 禁止寻找或调用不存在的“自动选择条款”脚本。
* 禁止让 `build_report_json.py` 代替模型选择条款。
* 候选集中已有可用条款时，不得绕过候选集自由发挥。
* 只有候选条款为空或明显不适用时，才允许按 `citation-rules.md` 的回退检索规则到 `references/` 中检索。

---

## 8. 最终 JSON 字段强约束

最终报告 JSON 必须通过 Skill 校验后才能生成 PDF/Word。

顶层字段必须包含：

* `submitter`
* `inspect_time`
* `report_id`
* `image_url_map`
* `scene_keywords`
* `severe_count`
* `general_count`
* `overall_evaluation`
* `severe_hazards`
* `general_hazards`
* `next_steps_reminder`

`severe_hazards` 和 `general_hazards` 中每条隐患必须包含：

* `index`
* `photo_name`
* `description`
* `standard_name`
* `clause_no`
* `clause_text`
* `remark`

字段要求：

* 使用 `photo_name`，不得使用 `photo_path`。
* `photo_name` 必须出现在 `image_url_map` 中。
* `description` 不得为空。
* `standard_name`、`clause_no`、`clause_text` 不得为空。
* `remark` 不得为空，不得填写“无”，统一填写：`建议按现场实际复核`。
* `severe_count` 必须等于 `severe_hazards` 数组长度。
* `general_count` 必须等于 `general_hazards` 数组长度。

---

## 9. PDF/Word 报告强约束

PDF/Word 报告中必须同时体现重大事故隐患和一般事故隐患。

同一照片对应多条隐患时，照片单元格必须进行 rowspan 纵向合并，禁止重复显示同一照片造成表格错乱。

报告文件链接必须使用 `report_generator.py` 返回的正式 `pdf_url` 或 `docx_url`，不得自行编造链接。

---

## 10. 总体禁止事项

* 禁止遗漏用户上传的照片。
* 禁止隐患描述为空。
* 禁止隐患没有规范依据。
* 禁止条款原文被改写、截断或概括。
* 禁止条款与隐患事实不匹配。
* 禁止备注为空或填写“无”。
* 禁止 Markdown 快速反馈展示一般事故隐患。
* 禁止 Markdown 快速反馈包含下一步工作提醒。
* 禁止图片引用本地路径。
* 禁止使用 `photo_path` 替代 `photo_name`。
* 禁止未通过最终 JSON 校验就生成 PDF/Word。
---

## 11. 重大事故隐患判定强约束

重大事故隐患判定必须严格引用《房屋市政工程生产安全重大事故隐患判定标准（2024 版）》等判定标准，不得将一般违规行为错误判定为重大事故隐患。

### 判定原则

1. **必须引用判定标准**：重大事故隐患必须对应《房屋市政工程生产安全重大事故隐患判定标准（2024 版）》中的明确条款，不得仅引用技术规范（如 JGJ 276、JGJ 80 等）作为重大隐患判定依据。

2. **禁止扩大化判定**：一般违规行为（如吊物下方站人、未系安全带、安全帽佩戴不规范等）不属于重大事故隐患判定标准情形的，应判定为一般隐患。

3. **客观证据原则**：照片中无法确认的项目（如安全装置是否失效、是否验收合格、是否达到报废标准等），不得直接判定为重大隐患，应注明"需现场进一步核查"。

### 常见错误判定（必须避免）

| 隐患描述 | 错误判定 | 正确判定 | 理由 |
|---------|---------|---------|------|
| 吊物下方站人 | 重大 | **一般** | 不属于重大隐患判定标准情形，属于违规操作 |
| 高处作业未系安全带 | 重大 | **一般** | 不属于重大隐患判定标准情形，属于违规操作 |
| 安全帽佩戴不规范 | 重大 | **一般** | 个人防护问题 |

### 重大事故隐患判定标准（起重吊装）

根据《房屋市政工程生产安全重大事故隐患判定标准（2024 版）》第八条，建筑起重机械及吊装工程有下列情形之一的，应判定为重大事故隐患：

- （一）起重机械设备未经验收合格即投入使用
- （二）基础承载力和变形不满足设计要求
- （三）安装、拆卸、爬升前未对结构件、安全装置进行检查
- （四）**安全装置不齐全、失效或者被违规拆除、破坏**
- （五）主要受力构件有可见裂纹、严重锈蚀、塑性变形、开焊
- （九）**使用达到报废标准的建筑起重机械或吊索具**

### 重大事故隐患判定标准（高处作业）

根据第九条，高处作业有下列情形之一的，应判定为重大事故隐患：

- （一）钢结构安装用支撑结构未按设计要求设置**防倾覆装置**
- （二）单榀钢桁架安装时**未采取防失稳措施**
- （五）**高处作业吊篮安全锁失效、安全绳未独立悬挂**

### 重大事故隐患判定标准（冒险作业）

根据第十五条，存在以下冒险作业情形之一的，应判定为重大事故隐患：

- （三）**使用起重机等非载人设备吊运人员**

### 需要现场核查的项目（照片中无法确认）

根据 `extra_checklist.json`，各类设备必查项目如下。照片中无法确认的，应在报告中注明"需现场进一步核查"，不得直接判定为隐患。

## 12. 规范版本强约束

禁止编造不存在的规范版本（如"非正式版"、"正式版"等）。

1. **唯一版本原则**：每个规范只有一个正式版本，不得使用"非正式版"等虚构版本名称。

2. **条款号核对**：同一规范的不同文件可能存在条款编号差异，必须使用正式发布的规范文件中的条款号。

3. **禁止混用**：不得将 A 版本的条款号与 B 版本的条款内容混用。

典型错误：
- ❌ 编造"JGJ 276-2012 非正式版"并使用其条款号 3.0.23
- ✅ 正确使用"JGJ 276-2012 建筑施工起重吊装工程安全技术规范"条款号 3.0.18

## 13. 条款引用验证强约束

引用规范条款前，**必须逐条验证**以下事项，禁止凭模型记忆直接引用：

### 验证步骤

1. **确认规范文件存在**：规范文件必须真实存在于 `references/` 目录中
2. **确认条款号存在**：条款号必须在该规范文件中真实存在
3. **确认条款内容匹配**：条款原文必须逐字复制，不得改写、截断、概括或补充
4. **确认规范版本最新**：优先使用 `references/` 中的最新版本，禁止引用过期规范

### 典型错误案例（必须避免）

| 错误类型 | 错误示例 | 正确做法 |
|---------|---------|---------|
| 编造条款号 | JGJ 59-2011 3.1.4（该规范无此条款） | 先检索规范文件，确认条款号真实存在 |
| 引用过期规范 | JGJ 46-2005（已过期） | 使用 JGJ 46-2024（references 中有最新版） |
| 条款号不完整 | JGJ 59-2011 3.2.3（子条款未标明） | 使用完整条款号如 3.2.3-3、3.2.3-4 |
| 凭记忆编造 | GB 7258-2017 8.1.1（references 中无此文件） | 如 references 中无此文件，需注明"需现场核实" |

### 强制要求

1. **mapping 库优先原则**：
   - **必须先执行 `match_hazard.py` 从 `major_hazard_mapping_v7.json` 自动匹配候选条款**
   - 禁止跳过 mapping 库匹配步骤直接手动填写候选条款
   - 候选条款必须来自 mapping 库，不得凭模型记忆编造
   - 只有 mapping 库中无匹配结果时，才允许到 `references/` 中检索

2. **references 优先原则**：
   - 优先从 `references/` 目录中的规范文件查找条款
   - 如 `references/` 中有多个版本，使用最新版本（如 JGJ 46-2024 优于 JGJ 46-2005）
   - 过期规范不应出现在 `references/` 中，如使用需特别说明

3. **条款号验证原则**：
   - 引用前必须通过 `grep` 或 `read_file` 确认条款号在规范文件中存在
   - 对于有子条款的条款号（如 3.2.3-1、3.2.3-2），必须使用完整子条款号
   - 禁止使用模型记忆中的条款号，必须实际检索验证

3. **条款原文复制原则**：
   - 条款原文必须从规范文件中逐字复制
   - 禁止改写、截断、概括或补充条款内容
   - 如条款内容与隐患事实不完全匹配，应寻找其他更合适的条款

4. **无法确认时的处理**：
   - 如 `references/` 中无相关规范，应注明"规范需进一步核实"
   - 如无法找到合适条款，应停止报告生成并说明原因
   - 禁止编造规范名称、条款号或条款内容

### 执行流程中的验证点

在 `match_hazard.py` 和 `build_report_json.py` 之间，模型必须：

1. 读取 `references/` 中的相关规范文件
2. 验证候选条款的条款号是否真实存在
3. 验证条款原文是否与规范文件一致
4. 确认使用的是最新版本规范
5. 将验证后的条款写入 `_state.hazards[].resolution`
